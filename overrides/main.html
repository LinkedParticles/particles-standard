Opt-in per site via `extra.goatcounter_code`, exactly like `social_image` above: the code is the subdomain — the `MYCODE` of `https://MYCODE.goatcounter.com` — and it is configured in that site's own `mkdocs.yml`, which is the single place it appears. Both published sites name the one `linkedparticles` GoatCounter site, which accepts both hostnames, so the two report into one dashboard. That is deliberate and settled: the front door's landing page and the docs site's guides are one funnel, and reading a funnel across two dashboards means reconciling two sets of numbers by hand. One dashboard is only legible because the recorded PATH carries the hostname, which is what the `path` setting below is for. GoatCounter keys a pageview row on the path alone — never the hostname — so without this the apex `/` and the docs `/` collapse into one row, merging away the one distinction the funnel asks about: which venue someone landed on, and whether they went on to the other. Rows instead read `linkedparticles.org/why/` and `docs.linkedparticles.org/user-guide/getting-started/`. A `path` callback is handed count.js's own default path and returns the value that is sent, so prefixing the host ADDS to the default instead of replacing it: the `` normalisation count.js already does, and the requested path on a 404, both survive. The alternative, `data-goatcounter-settings`, is JSON and JSON has no functions — it could only carry a build-time string, which a hostname is not for a page reachable at more than one, and a static per-page path would flatten every 404 onto `/404.html`. count.js runs `window.goatcounter = window.goatcounter || {}` on load, so an object set before the async tag survives it; setting just the one key (rather than assigning the object wholesale, as the upstream example does) leaves anything else on it alone.
